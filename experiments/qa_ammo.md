# Q&A 弹药库

## 为什么用 RAG 不用微调？
资料随时更新（换文档不用重新训练）；成本差 3 个数量级；答案可溯源（能指出处）。

## 阈值 0.45 怎么定的？
建"无答案卷"（3 个资料里没有的问题），看 top1 分数分布：有答案 0.526~0.773，无答案 0.245~0.384，
0.45 是 0 误杀 0 漏放的分界线。诚实承认：这是玩具语料的红利，真实数据要重标。

## 为什么混合检索？纯向量不行吗？
实证：纯向量把"RAG怎么让模型不瞎编"排错（语义漂移，top1 给了分块文档）；BM25 数关键词稳。
双通道 + RRF 融合后 Recall@1 变 1.00。

## LLM 当精排法官靠谱吗？
踩过坑：擦边文档下法官 7/10 翻车（主观飘移），修输入完整性后 10/10。真实系统会换 bge-reranker（交叉编码器）。
我的结论：硬数学抗噪，LLM 只能当辅助裁判，且要人工抽查。

## 忠实度裁判自己也判断过？
对——它把"分块大小怎么选"误判过不忠实（合理概括被当成新增结论），靠输出契约 + 合理改写规则修复。
所以评测要有"人工抽查"环节，不能全信机器。

## 分块大小怎么选？
语义完整 vs 细节保留的权衡。常见 200 字固定切块，进阶按标题/段落结构切。分块是"最值得实验的部分"。

## 系统怎么处理不知道的问题？
两级：L1 置信度闸门（top1 余弦 < 0.45 → 固定拒答句）；L2 prompt 兜底（资料没有就说不知道）。

## 整个项目花了多少钱？
全部 API 花费 X 元（实测），加历史估算也不到 1 元。嵌入模型 0.5 元/百万 token，生成 1 元/百万。

## 179 行怎么算的？
只算核心：embed/index/retrieve/generate 等 src/vision_rag 下的生产代码，不含评测和文档。

## 评测体系是什么？
三把尺子：evaluate（Recall/MRR + 无答案卷）、eval_faithfulness（忠实率）、demo_rerank（粗精排对比）。
每个命令一行跑，改动后全量回归。

## 能处理多大文档？
目前 4+2 篇玩具文档（7 个分块）。扩展路径：按结构分块、更大嵌入模型、向量库落盘，成本随 token 线性涨。

## 下一步计划？
真实数据重标阈值；换交叉编码器精排；评估自动化（不用 LLM 当裁判）；把成本计量做成仪表盘。
